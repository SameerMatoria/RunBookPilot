Summary

RunbookPilot turns written IT runbooks into tested, approved automation. An engineer uploads a Word, PDF or wiki runbook. An AI agent extracts the steps, writes a PowerShell or Ansible script, tests it in a sandbox, and sends it to an engineer for one-click approval.

Track fit: Track 01, Intelligent IT Services. The track asks for a challenge where automation replaces manual effort, with proof of how the work changes. RunbookPilot turns effort-led operations (people following documents) into automation. It measures the change for each runbook: minutes per run before and after, and error rate.

One-line pitch: "Every ops team has hundreds of runbooks nobody has time to automate. RunbookPilot automates them for you, and a human still signs off."

Business use case

The problem: routine operations still depend on documents and people. Managed-services teams keep large libraries of runbooks: restart a service, clear disk space, rotate a certificate, onboard a user, fail over a database. Engineers follow them by hand, many times a week, across many client accounts.

Why it stays manual. To automate a runbook, an engineer has to read it, write a script, test it safely and get it reviewed. That takes days per runbook, so only the most frequent runbooks get automated. The rest stay manual.

Current manual process: find the runbook → read it → log in to each server → run each step → check results → write notes. At each step, an engineer can skip a line, mistype a command or run it on the wrong server.

Impact and success metrics

The impact comes from two effects. Each automated run saves engineer time and removes human error. Converting a runbook also drops from days to minutes, so the long tail of rarely automated runbooks becomes worth automating.

Hours saved per year = Σrunbooks [ (manual min − automated min) × runs per year ] ÷ 60

Illustrative only, using assumed numbers: 20 runbooks, 30 minutes manual vs. 2 minutes automated, each run 10 times a week, gives about 4,850 engineer-hours a year. Replace these assumptions with your team's real runbook counts and frequencies before the pitch.

Beyond hours: fewer SLA breaches from slow manual work, a full audit trail of every automated action, and operational knowledge that no longer lives only in one senior engineer's head.

Solution overview

Seven steps take a runbook from document to approved automation, and a human approves before anything runs.

Three loops keep it safe: unclear steps go to the engineer, failed tests retry up to 3 times, and rejected scripts go back to the Author agent with the reviewer's feedback.

Architecture

Agents write and test code only in an isolated sandbox. A script reaches real servers only after an engineer approves it.

The web app and Teams talk to one backend API. The API starts the four-agent pipeline in Foundry, which reads documents, lints and tests in the sandbox, then sends a summary card to Teams. Only after approval does the API hand the script to Azure Automation or Ansible, which pulls it from GitHub and secrets from Key Vault at run time.

Main APIs

  • POST /runbooks: upload a document, returns runbook id
  • GET /runbooks/{id}: parsed steps, script, test results, status
  • POST /runbooks/{id}/regenerate: retry with reviewer feedback
  • POST /runbooks/{id}/approve and /reject: reviewer decision
  • GET /metrics: conversion rate, time saved, runs executed

Design doc

Four specialist agents, each with one job, pass structured JSON to the next. Separate agents make each step testable, and the demo can show exactly where a conversion succeeded or failed.

Agent roles

AgentInputOutputKey rule
ParserRaw runbook textOrdered steps: action, target, expected result, open questionsNever invent a step; flag anything ambiguous
AuthorParsed steps + target OSScript with one function per step, logging, dry-run modeEvery step has a check that it worked
TesterScript + sandboxPass/fail per step, logs, fix suggestionsOnly runs in the sandbox, never real systems
ReviewerEverything aboveSummary card: what it does, risks, test evidence, confidencePlain language a busy engineer reads in 1 minute

Script conventions the Author must follow

  1. Idempotent: running it twice does no harm.
  2. -WhatIf / --check dry-run mode by default.
  3. Pre-checks before changing anything; stop on first failure.
  4. Structured log line per step for the audit trail.
  5. No credentials in the script; read from Key Vault at run time.

Safety guardrails

  • The agent never touches production. It only writes code and runs it in a disposable sandbox.
  • Scripts that use blocked commands (disk formatting, mass deletes, firewall-wide changes) fail the lint gate.
  • Ambiguous runbook steps go back to the engineer as questions, not guesses.
  • Retry cap: at most 3 fix-and-retest loops, then hand over with notes.
  • Nothing executes for real until a named engineer approves it.

UI screens

  1. Upload: drag in a runbook, pick target OS and tier.
  2. Side-by-side review: original runbook step on the left, generated code on the right, and a test result badge for each step. This is the main screen of the demo.
  3. Questions: ambiguous steps the agent needs answered.
  4. Approve: summary card, test evidence, approve or reject with a comment (also in Teams).
  5. Impact dashboard: runbooks converted, runs executed, hours saved.

Build phases

  1. Prep (before the event): collect and anonymize 10 real runbooks; time a manual run of 3 of them; get Azure and Foundry access.
  2. Phase 1: Parser agent working on all 10 runbooks; sandbox runs a hello-world script.
  3. Phase 2: Author + Tester loop passing on at least 5 runbooks; UI upload and review screen.
  4. Phase 3: Approval flow, guardrails, metrics collected across all 10.
  5. Phase 4: Freeze features, rehearse the demo 3 times, record a backup video.

Demo script (5 minutes)

  1. The pain (30 s): show a real 12-step runbook and the manual time it takes.
  2. Upload (30 s): drop it into RunbookPilot.
  3. Watch it work (90 s): steps parsed, script written, sandbox tests turning green.
  4. Human in control (45 s): reviewer card, one ambiguous step flagged, approve.
  5. Run it (30 s): the approved script finishes in seconds.
  6. Proof (60 s): results across 10 runbooks and the yearly ROI for your account.
  7. Close (15 s): the pitch line.

How it maps to judging

  • Track fit: manual effort replaced by automation, with measured before/after.
  • Innovation: agents write and test the automation, not just suggest it.
  • Feasibility: built on generally available Microsoft services, with human approval required.
  • Business impact: hours saved, errors avoided, an audit trail, and reuse across accounts.
