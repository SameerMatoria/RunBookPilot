How RunbookPilot works

The architecture in one page, for explaining it during the demo: what each part does, how a runbook flows through the system, and what keeps it safe.

The one-liner Every ops team has hundreds of runbooks nobody has time to automate. RunbookPilot reads a runbook, writes the script, proves it works in a sandbox, and an engineer still signs off.

The big picture

Five layers. The engineer only talks to the web app. Four specialist AI agents do the work behind the API, and only the Tester ever runs code, inside a throwaway sandbox.

What happens when you upload a runbook

The same seven stages as the progress bar at the top of the app. Each card says what happens and gives one line you can say while it runs.

  1. 1
    Engineer

    Upload

    Drag in a PDF, Word, Markdown or text runbook. The backend pulls the text out of the file and starts the agents in the background, so the page stays live.

    "This is a real runbook. Today someone follows it by hand, step by step."
  2. 2
    Parser agent

    Extract the steps

    Turns the document into an ordered list: what to do, where, the exact command, and what success looks like. It sets a risk tier (low, medium or high). It is told never to invent a step.

    Code: backend/app/agents/parser.py
    "It understood all 8 steps and rated this medium risk because it restarts a service."
  3. 3
    Engineer

    Answer questions

    Vague steps like "make sure everything looks OK" are flagged. The engineer answers, and the answers go into the script.

    "It doesn't guess. When the runbook is unclear, it asks us, just like a new team member would."
  4. 4
    Author agent

    Write the script

    Writes a Bash script with one function per step. Every step checks its own result, the script is dry-run by default, it stops on the first failure, and it writes one log line per step. Then the lint gate blocks anything dangerous (formatting disks, mass deletes, firewall wipes, hard-coded passwords) and ShellCheck catches bugs.

    Code: backend/app/agents/author.py, backend/app/lint.py
    "Look at the side-by-side view: each runbook step on the left, the exact code for it on the right."
  5. 5
    Tester agent + sandbox

    Prove it works

    Each test starts a brand-new Linux server in Docker, with nginx running like a real app server. The script runs twice: first as a dry run, then for real with --execute. Each step reports pass, skip or fail. If it fails, the Tester reads the logs, explains the cause, and the Author fixes it. That loop runs up to 3 times, then hands over to a human.

    Code: backend/app/pipeline.py, backend/app/sandbox.py, sandbox/
    "These green badges aren't the AI's opinion. The script actually ran, restarted nginx, and got a 200 from the health page."
  6. 6
    Reviewer agent

    Summarise for a busy engineer

    A one-minute card: what it does, what it changes, risks with mitigations, confidence, and, importantly, what the sandbox did not test.

    Code: backend/app/agents/reviewer.py
    "It's honest about its limits. It tells us the log-cleanup branch never ran because the disk wasn't full."
  7. 7
    Engineer

    Approve or reject

    Approve with your name, and the script joins the automation library. Reject with a comment, and it goes back to the Author with your feedback. High-risk scripts need two different engineers. Every decision is recorded.

    "Nothing touches a real server until a named engineer approves it."

After approval: running on real servers

Approval is not the end. Operators run the approved script on managed servers, by hand, on a schedule, or when a monitoring alert fires. The same safety rules apply every time.

  1. A
    Admin

    Register servers once

    Add a credential (SSH key or password) and a server. The credential is encrypted before it is stored and can never be read back through the app. The first Test connection pins the server's SSH identity (host key); after that, a machine presenting a different identity is refused.

    Code: backend/app/routes/servers.py, backend/app/ssh.py, backend/app/secrets_store.py
    "It won't send a script to an impostor server, and nobody, not even an admin, can read the stored passwords."
  2. B
    Operator + worker

    Run the approved version only

    Only the exact approved script version runs (its SHA-256 fingerprint is recorded). Execute always does a dry run first and stops if that fails. High-risk scripts need a change ticket. Output streams live; every step reports pass, skip or fail; the script file is removed from the server afterwards.

    Code: backend/app/executor.py, backend/app/runs.py
    "Same green badges as the sandbox, but this time on a real server, with the full output and who started it."
  3. C
    Schedules and alerts

    Hands-off runs

    A schedule (cron) or a webhook from the monitoring tool starts the script automatically, with a cooldown so an alert storm doesn't run it fifty times. High-risk scripts can never auto-execute from an alert.

    "Disk-full alert at 3 a.m.? The approved cleanup runs and the on-call engineer sleeps."

Six layers of safety

The question every judge will ask: "What if the AI gets it wrong?" The answer is that no single layer has to be perfect.

1

Asks, never guesses

The Parser flags unclear steps as questions instead of inventing what they mean.

2

Dry run by default

Scripts only print what they would change unless explicitly run with --execute.

3

Lint gate

Blocks destructive commands and hard-coded passwords before anything runs, even in the sandbox.

4

Isolated sandbox

A fresh container for every run, no network, capped CPU and memory, a 2-minute time limit, deleted afterwards.

5

Retry cap

At most 3 automatic fixes, then a human takes over. The AI can't loop forever or fake a pass.

6

Human approval

A named engineer signs off; high-risk scripts need two. Every step and decision is logged.

Likely judge questions

Short answers you can give with confidence.

What if the AI writes a dangerous command?

Three things stop it. The lint gate blocks destructive commands before anything runs. The sandbox is isolated, has no network, and is deleted after every run. And nothing reaches a real server without a named engineer approving it.

What if the AI makes up steps that aren't in the runbook?

The Parser is told never to invent steps, and unclear ones become questions for the engineer. The side-by-side screen maps every line of code back to a runbook step, so anything extra is easy to spot during review.

How do you know the script actually works?

It really runs in a fresh Linux server, as a dry run and then for real. Each step writes its own pass/skip/fail line, and those lines drive the green and red badges. The app shows the actual sandbox output, not the AI's opinion.

Why four agents instead of one?

Each one has a single job and can be tested on its own. When a conversion fails, you can see exactly where: parsing, writing, testing or review. The Tester and Author also check each other's work.

Does it run on real servers?

Yes. Operators run approved scripts over SSH, by hand, on a schedule or from a monitoring alert. Only the approved version runs, a dry run always comes first, server identities are pinned, credentials are encrypted, and every run is logged with its full output.

Which AI model do you use, and what does it cost?

The prototype uses a free open model on Groq. The code works with any OpenAI-compatible model, so production would use Azure AI Foundry, which is a configuration change, not new code.

What about Windows servers and PowerShell?

The prototype focuses on Linux and Bash to do one thing well. The same design extends to PowerShell with a Windows sandbox VM and PSScriptAnalyzer as the lint gate. That's on the roadmap.

What's the business impact?

Two effects. Each automated run saves engineer time and removes typos and skipped steps. And converting a runbook drops from days to minutes, so the long tail of rarely automated runbooks becomes worth doing. Hours saved per year = Σ (manual minutes − automated minutes) × runs per year ÷ 60.
